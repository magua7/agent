# Skill catalog and trust policy

## Purpose

A Skill is untrusted procedural guidance. It can help a planner or agent decide
how to approach a task, but it cannot register tools, widen task scope, grant
approval, change run state, or weaken verification. Tool capabilities remain
owned by the registry and every action still passes the execution policy.

The repository catalogs 105 external non-white-box Skills plus one
project-owned local sample, without making external Skill text part of the
trusted kernel.
Discovery and authorization are deliberately separate:

```text
SKILL.md frontmatter        trusted policy.json
name + trigger description + enablement, task type, role, risk, capabilities
             \                /
              catalog descriptor
                      |
        bounded relevance selection
                      |
       untrusted workflow guidance
                      |
    scoped Tool Registry + Verifier
```

The lightweight wheel packages only the project-owned local sample and its
built-in policy. The external corpus remains a source-checkout asset and must
be supplied through an explicit `skills_root`; it is never discovered from the
current directory implicitly.

## Skill directory format

Every discoverable Skill occupies one direct child directory of the configured
root and contains a UTF-8 `SKILL.md`:

```text
skills/
  policy.json
  example-skill/
    SKILL.md
    SCENARIOS.md             # optional, explicitly linked resource
```

`SKILL.md` starts with bounded YAML frontmatter containing only discovery
metadata. The core adapter intentionally implements the small `name` and
`description` subset and does not add a YAML dependency:

```markdown
---
name: example-skill
description: >-
  Explain what the Skill does and the concrete situations that should trigger it.
---

# Example skill
```

The folder name must equal `name`. Legacy project-owned Skills with a strict
JSON `skill.yaml` remain readable during migration, but a sidecar never makes
an external root trusted by itself: normal loading still requires repository
policy, and the compatibility trust switch is off by default. New external
Skills do not duplicate their name and description in a sidecar.

## Imported corpus adaptation

Imported documents are rewritten for this runtime rather than used as
Claude Code instruction files. Every cataloged `SKILL.md` has a managed
`ZhiyuGo workflow` block immediately after its title. That block mirrors the
entry's role, risk class, and default state for model context, while
`policy.json` remains the only trusted source of those values.

The body contract differs by role:

- routers return an observation, at most two canonical Skill names, and the
  next evidence needed; names are routing hints, not dynamic imports;
- orchestrators return an evidence-gated stage graph and record unsupported
  operations as capability gaps instead of invoking browsers, MCP servers,
  shells, or sub-agents;
- leaf workflows separate facts from hypotheses, cite Evidence IDs, and obey
  the risk-specific active or isolated-lab boundary;
- the quality gate returns a bounded verdict and never upgrades impact beyond
  cited evidence.

Long linked-resource leaf documents keep their decision workflow in
`SKILL.md` and move advanced examples to same-directory
`TECHNIQUE_REFERENCE.md`. Each companion Markdown file has a managed notice
and table of contents and must be linked directly from the main document.
Resources are available through explicit catalog resource tooling; they are
not recursively or automatically inserted into an active Run.

The migration is reproducible and idempotent:

```powershell
python -X utf8 -B scripts/adapt_skill_corpus.py --root skills
python -X utf8 -B scripts/adapt_skill_corpus.py --root skills --check
```

The managed marker blocks are generated by this script. Edit role/risk policy
in `policy.json`; edit project-specific workflow prose outside the markers.

## Trusted policy

External frontmatter never grants permission. `skills/policy.json` is the
repository-owned control plane. Version 1 groups Skills with these fields:

| Field | Meaning |
|---|---|
| `skills` | Exact directory names covered by the group |
| `enabled` | Eligible for normal automatic selection |
| `task_types` | `generic`, `pentest`, `incident_response`, `code_audit`, `reverse_analysis`, or `ctf` |
| `role` | `router`, `leaf`, `quality_gate`, or `orchestrator` |
| `risk_class` | `passive`, `active`, or `lab_only` |
| `required_capabilities` | Existing abstract capabilities; never tool names or permission grants |
| `human_approval_required` | Warning propagated with guidance; metadata alone never authorizes a tool |
| `resource_loading` | `metadata_only` or bounded `linked_markdown` |

Each directory must be covered exactly once or explicitly excluded with a
reason. An unclassified, malformed, linked, or oversized entry is diagnosed and
disabled. Normal runtime isolates that directory and continues; strict catalog
validation fails the whole catalog for CI and release checks.

## Risk classes

- `passive`: routing, quality gates, static methodology, cryptanalysis, and
  offline forensics guidance. It may be enabled by default.
- `active`: guidance that can cause network interaction or state-sensitive
  validation. External active groups are disabled until explicitly curated for
  the deployment, and their policy requires human approval. A project-owned,
  tightly scoped Skill such as loopback-only service discovery may be enabled,
  but it remains subject to task scope and Tool Registry policy.
- `lab_only`: exploitation, shells, persistence, credential access, lateral
  movement, tunneling, defense evasion, or escape techniques. It is excluded
  from normal selection even when present and can only be inspected through an
  explicit lab-only catalog mode. The current runtime provides no capabilities
  for these operations.

`allowed-tools` or command examples embedded in an external Skill are treated
as untrusted text. They cannot affect the registry or execution policy. The
`human_approval_required` flag is risk metadata, not an implemented approval
gate and not a capability grant.

## Selection and progressive disclosure

The provider performs a bounded validation/hash pass, retains catalog metadata
rather than every body, filters by task type, enablement, available
capabilities, and risk, then ranks against the task objective. Only a small
stable top-k set of bodies is retained or exposed to planner/agent context. A
single malformed Skill must never cause an otherwise valid run to fail.

The runtime freezes that selected tuple for the lifetime of one Run and emits a
`skills_selected` audit event containing each name, trusted policy snapshot,
and the provider-supplied content hash. The filesystem provider always supplies
the `SKILL.md` SHA-256; a custom provider that omits it is recorded as `null`.
Planning and later Agent contexts therefore use the same guidance revision when
the selected provider supplies immutable content identities.

Catalog and document caches change only through the explicit `refresh()` API;
deployments must call it atomically after a policy update or restart the
runtime. A selected document whose file identity or digest changed after the
index was built fails closed instead of silently using mixed revisions.

The main `SKILL.md` body is bounded. Only Markdown resources directly linked by
that body may be read, and resource reads enforce the same root-containment,
link/reparse-point, UTF-8, and byte limits as the main document. Files are not
recursively injected into model context.

## Deferred white-box package

`php-audit-skills` is intentionally excluded and ignored by Git for now. It is
a nested project with executable PHP/shell tools, environment mutation,
multi-agent orchestration, and a separate trust lifecycle. Supporting it later
requires an independently reviewed plugin or constrained process, not the text
Skill adapter.

`code_audit` remains a valid runtime task type, but no Skill from this deferred
white-box package is classified or selected by the current catalog.

## Provenance

The core implementation remains independently developed. External Skill text
has a separate provenance and usage-rights lifecycle. Before sharing or
redistributing a Skill corpus, record its source, revision, integrity digest,
and applicable terms. A private repository does not turn external content into
project-owned material.

## Current execution limit

The local runtime exposes only `network.scan`, `http.request`, `file.read`,
`file.search`, and the same file-search adapter's `code.search` alias.
Cataloging a Skill whose examples mention another tool makes the guidance
discoverable; it does not make that operation executable. Additional
capabilities require a separately implemented Tool adapter and policy review.
